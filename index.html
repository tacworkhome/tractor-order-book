The shape of it

Everything lands as one order, with one number

Your Counter, Kiosk, Catering and Order channels already write to the order desk. The missing pieces are three inbound connections and two outbound ones. All five meet at a single order book that owns the state of every ticket.

01 · DoorDash and Uber Eats

Both have an official door in. Both gate it.

"No middleman" has two meanings: no tablet in the kitchen, and no aggregator taking a monthly fee per store. Both are reachable. The marketplace commission itself stays, because that is what you pay them for customers.

DoorDash

Marketplace API, order injection

  • Orders are pushed to a webhook on our server, and we confirm or reject them.
  • Access is by application and approval through the developer portal. No public timeline.
  • Single-merchant integrations use the Store Onboarding Webhook, and a Business Admin approves each store in the Merchant Portal.
  • Their graduation bar is high: about 98% successful injection over 14+ days. That is built for multi-store vendors, which is a mismatch for one brand.
Uber Eats

Marketplace API, POS integration

  • Orders arrive as a webhook. We return HTTP 200, then must accept or deny within about 11.5 minutes or the order auto-cancels.
  • Start in a sandbox. Production needs an NDA, an API licence agreement and written approval through an Uber partner manager.
  • Go live per store by switching POS integration on for a pilot store first.
  • Only one primary webhook URL per app, so routing by store happens on our side.

The part we own regardless of approval

One adapter per channel, one state machine

Ingest

A small webhook service per marketplace. It verifies the signature, stores the raw payload untouched, maps it to Tractor's order shape and writes it to the order book. The raw copy means we can replay anything.

Idempotency

Marketplace order id plus store id is a unique key. Retries and duplicate webhooks cannot make two tickets.

Accept rules

Auto-accept when the kitchen is under a load limit and every item is in stock. Otherwise alert a human well inside the 11.5 minute window, and deny with a reason before it times out.

Status

received → accepted → printed → preparing → ready → picked_up, plus failed and cancelled. Status changes are sent back to the platform, so riders are dispatched at the right moment.

Printing

Print when the order lands, and know when it did not

  • Printers poll us. Epson's Server Direct Print has the printer fetch jobs from our server, so no open ports, no static IP and no kitchen network changes. Epson notes the printer checks on an interval, so the print queue is the source of truth, and polling is set short.
  • One queue, routed by station. Each line item maps to a station (grill, cold, expo). The same order prints a chit per station plus an expo summary.
  • Printing is a tracked status, not a hope. A job moves queued → fetched → printed. If an accepted order is not printed within 45 seconds, staff get an alert and the order goes to a reprint screen.
  • Dead printer plan. The same ticket shows on the kitchen screen. A one-tap reprint exists for every order.
  • I would prove it with the pilot store's real printer and a test order from each sandbox before January, and measure order-received to chit-printed time.

03 · The idea I want to try

A payout auditor that nobody has to remember to run

Marketplaces take commission, fees, promotions and adjustments, then pay out in batches. Errors, missing items refunded to guests and wrong fees are routinely absorbed because checking is tedious. Your own order book is the one source that knows what should have been paid.

First small experiment (a week, no integration needed)

  • Export last month's payout reports from DoorDash and Uber Eats.
  • An agent matches each line to what the kitchen actually made, flags mismatches (fee rate off, order missing, refund without a dispute) and drafts the support message with evidence attached.
  • A person reviews and sends. Measured by dollars recovered per month and minutes saved.

It is the one place AI is clearly cheaper than a person, it pays for itself in a measurable number, and it proves the "fees and payouts" box on your diagram. Next after that: a kitchen-load agent that pauses a marketplace store when the line is overloaded.

05 · Your taste

Something I built and run: InsiderAct

insideract.com is an AI-native research platform I built alone and launched in July 2025. It reads SEC insider filings, filters out the noise, and shows a short list of high-conviction signals. Behind it are agentic research workflows on the Claude API with cited answers, and millions of insider-transaction records from EDGAR and market data in one Postgres layer. It is built with Next.js, TypeScript, Supabase and Vercel.

Why it looks right to me

  • One accent, one meaning. Green means "act" and "buy" everywhere, so colour is never decoration.
  • Every signal is scored and labelled (for example 80/100, Very Strong), so ten of them can be compared in seconds.
  • The filtered few come first. The page leads with the strongest signals and lets people go deeper, instead of showing every filing at once.

It is also the closest thing I have to your problem: messy outside data in, one clean record per item out, and a person who has to trust it.
